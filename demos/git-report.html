# On Rewriting Nobody writes well on the first try. A first draft is not a failed final draft; it is a probe, thrown out quickly so that there is something real to push against. The quality of a piece is decided by what happens next — by the rewriting. Most writing advice is about producing words. Almost none of it is about what happens afterwards, which is where the actual work is. You write a paragraph, read it back, and fix it. Then you fix it again. The distance between a first draft and a published piece is measured in these small, repeated acts of repair. Every document has its contested sentences: the ones rewritten on every pass, never quite settling. They are worth watching very closely, because they mark the exact places where the thinking is still happening. Editors know this in their bones. Programmers know it too, though they call it refactoring. In both crafts, the object on the screen is the residue of hundreds of decisions, most of them reversals. A codebase, like an essay, remembers nothing by default; version control had to be invented to give it a memory. The tools we use to write mostly hide this history. A document shows you its present tense only: the current text, flat and confident, with no trace of the arguments that produced it. If we could see where a text had been worked and reworked — which sentences came easily and which were fought over — we would read it differently, and we would edit it better. This essay is an argument for tools that remember.
